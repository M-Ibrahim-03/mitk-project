# Veil against the hackathon problem statement

**Research date:** 2026-10-10  
**Scope:** Compare the supplied challenge brief with the current repository and primary technical/privacy sources. This is research and recommendations only; it does not claim a security certification or universal PII coverage.

## Judge-focused assessment

Veil has a strong, judge-friendly core: a real middleware boundary, recursive text/JSON handling, reversible task-scoped tokens, a fail-closed egress check, a local simulated sink that captures what it received, response restoration, and a same-run workflow view. Those features map directly to the expected deliverables.

The main weakness is evidence breadth. The checked-in benchmark snapshot reports **22/22 planted values detected, zero false positives, zero originals at the mock tool, 22/22 restored, and p50/p95 0.490/1.206 ms—but only across 8 cases**. The corpus contains email, person-name, phone, student-ID, and UPI examples. It does not benchmark all the other formats README lists (such as Aadhaar, bank account, card, PAN, IFSC, or IBAN); it also has few benign controls and does not plant PII in JSON object keys. A perfect score on this curated set is useful evidence for the demo formats, not a general detection rate. [The current benchmark snapshot](benchmark-results.md), [corpus](data/benchmark.json), [evaluator](veil/evaluation.py), and [README](README.md) are the repository evidence.

**Recommendation:** Present Veil as a working prototype with measured, explicitly bounded coverage. The highest-value improvement for judging is a larger, independently varied synthetic test set and an auditable results page—not a claim that the current detector handles “almost all” personal information.

## What the sources imply for a stronger evaluation

### 1. Score exact spans and per-type errors, not just a headline percentage

**Source fact:** The Presidio Research evaluator reports precision, recall, and F-scores both globally and by entity type; its span evaluator considers entity boundaries and types, and distinguishes strict matching from partial overlap. The project also provides synthetic data generation and warns against letting the same generated template appear across dataset splits. ([Presidio Evaluator metrics](https://presidio-research.dataprivacystack.org/evaluation/), [span-evaluation details](https://github.com/data-privacy-stack/presidio-research/blob/main/docs/span_evaluation.md), [synthetic generation and split guidance](https://github.com/data-privacy-stack/presidio-research))

**Veil comparison:** `veil/evaluation.py` already matches exact `(path, start, end, entity_type)` spans and calculates aggregate precision/recall, false positives, and per-type recall. That is a solid base. The saved report does not show per-type precision/F1, and the 8-case corpus is not split into a separate held-out set.

**Recommendation:** Keep exact-span scoring as the primary number, add per-type TP/FP/FN, precision, recall, and F1, and preserve the raw counts beside percentages. Create a held-out set whose templates and synthetic value families do not appear in the tuning/examples set. Include enough safe negatives to make precision meaningful. Explain that the held-out synthetic set tests generalization only to its designed formats.

### 2. Prove leakage at the recipient boundary, independently of the detector

**Source fact:** NIST frames PII protection around preventing inappropriate access, use, and disclosure and recommends context-based safeguards. ([NIST SP 800-122](https://csrc.nist.gov/pubs/sp/800/122/final))

**Veil comparison:** The local mock tool’s captured request is an unusually strong demo asset because it proves what reached the recipient rather than only showing what the sanitizer intended to send. The benchmark checks original planted strings at their expected paths, while the gateway performs its own residual-detection check.

**Recommendation:** Use two independent assertions: (1) the production egress verifier passes, and (2) a test-only literal scan of the exact sink receipt finds none of the planted originals anywhere in keys or values. Add a spy assertion that a blocked request made zero tool calls. This lets a judge inspect a concrete boundary artifact instead of trusting a “redacted” badge.

### 3. Describe tokens as pseudonyms and protect the mapping

**Source fact:** GDPR defines pseudonymisation as processing that requires separate “additional information” for attribution and says that information must be kept separately with safeguards. It also calls out pseudonymisation and data minimisation as design measures. ([GDPR Article 4(5), Article 25](https://eur-lex.europa.eu/eli/reg/2016/679/)) The PCI SSC tokenization guidance—specific to payment-card systems, not a general certification for Veil—treats reversible token mapping, access control, and the overall implementation as security-critical; a token alone is not the whole security story. ([PCI SSC Tokenization Product Security Guidelines](https://www.pcisecuritystandards.org/documents/Tokenization_Product_Security_Guidelines.pdf))

**Veil comparison:** README and context correctly call tokens reversible pseudonyms, not encryption. A task-scoped in-memory vault is a good prototype boundary. In the current implementation, token strings include 40 random bits (`secrets.token_hex(5)`); this is not encryption, and the vault is what makes restoration possible. Local run evidence can also retain the original synthetic prompt.

**Recommendation:** State the threat model plainly: the mock tool sees opaque values; Veil’s trusted process holds the mapping temporarily; a compromise of that process or mapping can reveal the originals. For production-style hardening, increase token entropy, explicitly handle collisions, authorize every restore operation, and enforce expiry/clear-on-close. Keep raw inputs out of logs and persistent evidence by default. OWASP explicitly recommends removing, masking, sanitizing, hashing, or encrypting sensitive PII and secrets in logs. ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html))

### 4. Make the latency number reproducible and scoped

**Source fact:** Python documents `time.perf_counter()` as a high-resolution counter for measuring short durations. The `pyperf` project advises checking benchmark stability, collecting multiple runs/values, and using median/MAD when results are unstable. ([Python `time` docs](https://docs.python.org/3/library/time.html), [pyperf analysis guidance](https://pyperf.readthedocs.io/en/latest/analyze.html))

**Veil comparison:** `VeilGateway` uses `perf_counter` around sanitize plus egress verification, and `veil/evaluation.py` reports p50/p95 from one latency per each of 8 cases. That is the right scope for “added privacy-processing latency,” but not enough samples for a robust headline and not an end-to-end Gemini latency.

**Recommendation:** Report middleware-only latency and total workflow latency separately. Run repeated measurements per representative payload-size bucket after warm-up; include environment, number of samples, median, p95, and a variability measure. Keep Gemini network time out of the middleware metric. Re-run on the presentation machine and label the result as a local prototype measurement.

## Highest-value changes before judging

1. **Expand and freeze the synthetic evaluation set.** Cover every type advertised, structured and natural-language contexts, benign lookalikes, repeated occurrences, nested arrays/objects, and supported obfuscations. Split by template/value family and publish the set size and per-type raw counts.
2. **Make the evidence auditable in one command.** Print per-type TP/FP/FN/precision/recall/F1, leakage at the sink, restoration exactness, middleware latency distribution, and environment metadata. Keep benchmark output consistent with `data/benchmark.json`; the existing snapshot’s 100% result must stay explicitly scoped to its 22 planted spans.
3. **Lead with exact-boundary evidence.** In the live workflow show: protected prompt/tool request, egress verdict, captured sink receipt, protected tool result, local restoration, and final answer for one run. Include one blocked case where the sink call count stays zero.
4. **Explain utility and scope.** Keep `TICKET-DEMO-1042` as the valid end-to-end helpdesk example, while a separate synthetic gateway example demonstrates general structured payload handling. Explain that the prototype detects selected patterns, not all PII; detector recall is only measured for the planted corpus.
5. **Avoid relying on a live provider call for the core score.** The latest checkpoint in `context.md` records a Gemini final-answer `ServerError` and says a successful live run after retry changes remains to be observed. The challenge does not require an external LLM. Use the offline path for a reproducible privacy-boundary demonstration, and label Gemini as optional only when the same-run evidence succeeds.

## Bottom line

Veil already satisfies the core *shape* of the challenge and has stronger visual boundary evidence than a redaction-only demo. Its strongest winning argument is “here is exactly what the recipient received, here is proof the planted originals were absent, and here is the correctly restored trusted answer.” The main improvement is to make that argument statistically credible, precisely scoped, and repeatable. Do not present the current 22/22 benchmark as general PII coverage, equate reversible tokens with encryption, or claim the live Gemini path is verified from the latest failed run.
